# AI Pulse · GitHub에서 이어 쓰는 운영 지침

이 문서는 `shinnarag/ai-brief`의 **`source` 브랜치**만 읽고 다음 브리프를 작성·저장·검증하기 위한 독립 운영 기준입니다. 별도 컴퓨터에 있던 원본 폴더, 과거 프롬프트, 수집 스크립트를 전달받을 필요가 없습니다. GitHub 파일을 직접 읽고 수정할 수 있는 AI 도구라면 로컬 복제도 필수가 아닙니다.

2026-09-16에 제공된 인계서의 편집 기준, 저장소의 브리프와 실제 빌드 코드를 바탕으로 새로 정리했습니다. 예전 프롬프트와 충돌하는 GA 표제어·내부 용어·사건 중복 기준은 더 최근 인계서 기준으로 통일했습니다. 이전 자동화의 미확인 코드와 실행 상태를 복원한 문서는 아닙니다. 이후 사용자가 수정한 기준은 이 문서에 반영하여 다음 작업자에게 전달합니다.

## 1. 다른 컴퓨터에서 시작하는 요청

아래 요청과 이 문서의 링크를 AI 도구에 전달합니다. 날짜는 실제 작성 대상일로 바꿉니다.

```text
GitHub shinnarag/ai-brief 저장소의 source 브랜치를 열어 주세요.
AGENTS.md와 docs/brief-workflow.md를 읽고 YYYY-MM-DD AI Pulse 브리프를 작성해 주세요.
기존 브리프를 확인해 중복을 피하고, 웹에서 최신 출처를 직접 확인해 주세요.
완성한 원문을 source 브랜치에 저장하고 해당 커밋의 Actions 빌드 결과를 확인해 주세요.
완료 보고에는 원문 링크·커밋·검증 결과·사이트 게시 여부를 구분해 주세요.
```

- [원문 폴더](https://github.com/shinnarag/ai-brief/tree/source/briefs)
- [작성 템플릿](brief-template.md)
- [브랜치별 Actions 실행 기록](https://github.com/shinnarag/ai-brief/actions?query=branch%3Asource)

## 2. 필요한 기능과 현재 완료 범위

| 필요한 기능 | 용도 |
|---|---|
| GitHub `source` 파일 읽기 | 지침·최근 브리프·용어사전 확인 |
| 웹 검색과 원문 페이지 열기 | 새 뉴스의 사실·발표일·가용 범위 확인 |
| GitHub 파일 쓰기 권한 | 완성한 Markdown 저장·커밋 |
| Actions 결과 읽기 | 해당 커밋의 빌드 성공 여부 확인 |

GitHub 연결이 읽기 전용이면 초안 작성까지 가능합니다. 쓰기가 실제로 가능한지 확인하고, 저장하지 못했다면 초안과 미완료 이유를 전달합니다. 웹 접근이 없으면 최신 뉴스를 검증할 수 없으므로 완성된 당일 브리프라고 주장하지 않습니다. 특정 AI 회사나 API 키는 이 수동 작업 방식의 전제조건이 아닙니다. 선택한 도구의 이용 조건은 따릅니다.

현재 흐름은 **AI가 리서치·작성 → `source`에 원문 저장 → GitHub Actions가 빌드 검사**입니다. 이 문서 자체는 실행 프로그램이 아닙니다. 다른 컴퓨터 또는 클라우드 AI가 작업하면 원래 컴퓨터는 꺼져 있어도 됩니다. 모든 컴퓨터를 끄고 정시에 자동 생성하려면 별도의 클라우드 실행기·모델 호출·예약 설정이 필요합니다.

현재 `source`의 빌드 검사는 사이트를 배포하지 않습니다. 공개 사이트는 기존 `main` 배포 경로를 사용합니다. 새 원문이 GitHub에 저장되어도 웹사이트에 게시됐다고 보고하지 않습니다.

## 3. 시작 전: 날짜·기존 파일·수집 범위

1. 저장소와 브랜치가 위의 `source`인지 확인합니다. 최신 커밋을 읽고, 이미 작업 중인 변경이 있으면 보존합니다.
2. 날짜 기준은 `Asia/Seoul`입니다. 사용자가 날짜를 지정하면 그 날짜를 사용하고, 없으면 현재 KST 날짜를 확인합니다. 평일 브리프가 기본입니다. 별도 요청 없는 주말 실행은 생략하되, 사용자가 지정한 주말 특별판은 작성할 수 있습니다. 미래 날짜의 뉴스를 미리 만들어 내지 않습니다.
3. `briefs/` 목록을 날짜순으로 확인합니다. 대상 파일이 이미 있으면 내용·출처·해당 커밋의 빌드 상태를 먼저 검토합니다. 정상본은 재작성하지 않고 링크와 상태를 안내합니다. 오류 수정 또는 추가 취재 요청이면 기존 파일을 수정하고 변경 이유를 남깁니다.
4. 대상일 이전의 최근 2개 브리프를 모두 읽고, 최근 5개에서 이미 다룬 제목·원문 URL·제품 상태를 확인합니다. 오래된 베타나 예고가 다시 등장하면 전체 `briefs/`에서 제품명과 URL을 검색합니다. 과거 글은 형식·중복 확인 자료이며 사실 검증을 대신하지 않습니다.
5. 이번 수집 종료 시각을 KST로 기록합니다. 직전 브리프의 실제 수집 시각부터 이번 시각까지를 기본 범위로 잡습니다. 평일은 보통 약 24시간, 월요일은 금요일 수집 이후 주말을 포함해 약 72시간입니다. 이전 수집 시각이 없으면 최근 24시간, 월요일은 최근 72시간을 사용하고 추정한 범위임을 표시합니다.
6. 누락된 날이 있으면 마지막 정상 브리프 이후까지 범위를 넓혀 확인하고 `범위:`에 실제 시작·종료를 적습니다. 과거 날짜별 파일을 임의로 소급 생성하지 않습니다. 과거 날짜 작성 요청은 그날까지 공개된 자료만 사용하고, 실제 조사 시점과 대상 기간을 구분합니다.

수집 범위를 약간 겹쳐 확인해도 되지만, 전날 이미 다룬 동일 사건은 아래 중복 기준으로 제외합니다. 기존 운영의 예약 활성 여부를 이 문서만으로 추정하거나 새 예약을 자동 등록하지 않습니다.

### 후보별 확인 기록

후보마다 다음을 기록합니다. 로컬 작업이면 공개하지 않는 `logs/research-YYYY-MM-DD.md`를 쓸 수 있습니다. GitHub 파일만 편집하는 도구라면 작업 메모로 유지하고, 최종 원문의 출처·범위·스윕 줄에 확인 근거를 남깁니다. 임시 메모가 다음 컴퓨터에도 남아 있다고 가정하지 않습니다.

- 제목, 직접 확인한 URL, 원문 발표 시각과 KST 환산, 이번 범위에 해당하는 이유.
- 무엇이 달라졌는지, 지원 지역·계정·플랜·API, 베타/대기 명단/점진 도입/GA 중 현재 상태.
- 숫자·가격의 단위와 조건, 출처가 공식인지 보도인지, 확인할 수 없는 부분.
- 이전 브리프의 동일 사건과 차이, 채택할 카테고리 또는 제외 이유.

원문 발표일·본문·공식 계정 시각을 우선합니다. 검색 노출일이나 `dateModified`만으로 오늘 뉴스로 취급하지 않습니다. 프로모션은 발표일이 수집 범위에 들어오고, 현재 공식 가격표나 제품 화면에서도 활성임을 확인해야 합니다.

접근 실패·날짜 불명·유료벽은 `확인 불가`로 구분합니다. 직접 읽지 못한 페이지에 대해 `확인 완료`나 `새 소식 없음`이라고 쓰지 않습니다. 대체 출처를 찾되, 핵심 사실을 확인할 수 없으면 확정 뉴스로 올리지 않습니다. 루머·보도는 해당 신뢰도를 표시합니다.

헤더의 `> 스윕:`에는 확인 대상·최신 발표 날짜·새 소식 유무·접근 실패를 짧게 기록합니다. 새 소식이 없는 벤더의 메모는 이 줄에만 두고 본문 카드를 만들지 않습니다. 현재 화면에서는 이 인용문이 생략될 수 있으므로 중요한 불확실성은 해당 카드에도 적습니다.

## 5. 편집 기준

독자는 콘텐츠·제작·마케팅 실무자입니다. 제품이 무엇이고 실제 어떤 일을 바꾸는지 먼저 설명합니다.

- 한국어 **해요체**를 씁니다. 짧은 명사 조각이나 속보 여러 개를 한 불릿에 몰아넣지 않고, 사실 → 적용 범위 → 실무 영향이 이어지게 씁니다.
- 영어 문장 직접 인용을 넣지 않습니다. 의미·이유·비유를 한국어로 풀되 제품명·모델 ID·코드네임·고유명사·숫자·URL은 정확히 유지합니다. 예를 들어 `Ox`를 동물 이름으로 번역하지 않습니다.
- `왜 중요한가`라는 별도 라벨, `스텔스`, `프레임이 닫히는 축`, `상태 업그레이드`, `창 안`, `스테이징`, `워치`, `쿼터`, `bypass` 같은 내부 용어를 독자 문장에 쓰지 않습니다. `사용량`, `시험용 앱`, `이번 수집 기간`처럼 구체적으로 씁니다.
- 기존 비스킷 용어는 사전 표제어 그대로 씁니다. `GA`, `ZDR`, `WER`, `MCP`, `샌드박스`, `오픈웨이트` 등을 괄호 풀이로 반복하지 않습니다. 제품의 실제 공개 범위는 별도 문장으로 설명합니다.
- 주요 카드는 출처 줄을 제외하고 최소 4개, 가능하면 5~6개의 실질적인 불릿으로 씁니다. 확인 내용이 적은 작은 소식은 1~2개 불릿의 짧은 카드로 남길 수 있습니다. 반복 문장으로 분량을 채우지 않습니다.
- 충분한 소식이 있으면 본문 약 **8~12개 카드**를 목표로 합니다. Top 5는 본문 개수에 포함하지 않습니다. 카드 수에 맞추려고 검증한 유용한 소식을 버리거나, 반대로 빈 소식·추측을 보충하지 않습니다. 부족한 날은 부족한 이유를 완료 보고에 남깁니다.
- 출시를 가격·사용량 한 줄로 축소하지 않습니다. 무엇을 만드는 제품인지, 무엇이 새롭고 누가 쓸 수 있는지 설명한 뒤 가격 조건을 적습니다. 추정·비교·벤치마크는 출처의 주장과 자체 해석을 구분합니다.
- Top 5는 제품 GA, 제작용 모델·에이전트, 음악·음성, 크리에이티브 도구, 브랜드·캐릭터·숏폼 실무를 우선합니다. 후속 소송·펀딩·규제만으로 채우지 않습니다. 검증한 사건이 5개 미만이면 순위를 억지로 채우지 않습니다.
- 본문의 중요한 조건은 Top 요약에서도 유지합니다. 추정 가격을 확정 가격처럼, 보도를 공식 발표처럼, 베타나 일부 지역 도입을 전면 공개처럼 요약하지 않습니다.
- 마케팅·SNS도 조사합니다. 각 SNS 카드에는 실제 확인한 URL을 최소 1개 넣습니다. 별도 사건이나 확인한 반응이 없으면 다른 카테고리의 기사를 복제하지 않습니다.
- 초안 뒤에 후보 메모를 다시 읽어 누락을 점검합니다. 적합한 소식은 주요/짧은 카드로 남기고, 중복·오래된 내용·검증 실패로 제외했다면 이유를 기록합니다.

## 6. 중복과 예고·베타의 후속 확인

중복 검사는 AI가 다음 기준으로 수행합니다. 저장소에 없는 과거 `dedupe` 스크립트나 `prompt.run.md`를 찾느라 작업을 중단하지 않습니다.

1. 같은 원문 URL이나 같은 발표 사건은 가장 적절한 카테고리의 **본문 카드 하나**에 모읍니다. 모델·콘텐츠·SNS에 같은 발표를 나누어 싣지 않습니다. 서로 다른 확인 근거와 관점은 같은 카드 안에 합칩니다. 하나의 누적 변경 기록 URL에 서로 다른 날짜·제품의 독립 발표가 함께 있으면, 발표 항목을 구분할 수 있는 근거와 링크를 기록해 별개 사건으로 판단할 수 있습니다.
2. Top 5는 본문으로 이동하는 색인입니다. 제목과 한 줄 요약만 쓰고, 본문 불릿·출처 목록을 다시 싣지 않습니다. **Top 제목과 연결될 본문 제목을 정확히 같게** 써서 기존 화면에서 짧은 중복 카드가 생기는 것을 피합니다.
3. 참고 링크 표에 출처 URL을 다시 적는 것은 허용합니다. 본문 카드끼리의 중복과 혼동하지 않습니다.
4. 최근 브리프의 URL과 사건을 대조합니다. URL의 추적 파라미터나 다른 매체의 재보도만 달라진 같은 사건은 신규로 세지 않습니다. 같은 URL의 문서가 실질적으로 갱신됐다면 변경 내용·발표 시각을 확인해 후속으로 설명합니다.
5. 처음 확인된 베타·대기 명단은 소식이 될 수 있습니다. 이미 다룬 베타의 반복 소개는 제외하고, GA·대상 확대·실제 API 제공·요금 확정 같은 변화가 있을 때 그 차이를 씁니다. 과거의 `미확인` 메모가 오늘 확인된 출시를 막아서는 안 됩니다.
6. 별도 최신 관심 목록이 없어도 최근 원문에서 예고·베타를 찾아 확인하고, 후보가 다시 등장하면 전체 원문을 검색합니다. 과거 인계서에 적힌 제품 상태를 현재 활성 상태라고 단정하지 않습니다. 연속 작업에 필요한 상태·출처는 해당 브리프의 카드에 남깁니다.

## 7. 파일 형식과 화면 보존

[템플릿](brief-template.md)을 복사해 `briefs/AI-Daily-YYYY-MM-DD.md`로 저장합니다. 파일명·H1·수집 기간의 날짜를 맞춥니다. `주제:`, `주제 설명:`, `실무 액션:`, `수집 시각:`, `범위:`는 첫 25줄 안에 둡니다.

- 카드는 `1. **제목**` 형식이며 설명·출처는 들여쓴 `-` 불릿입니다. 일반 문단과 `###` 소제목은 카드 본문에 표시되지 않을 수 있습니다. 화면에는 내용 불릿이 최대 8개 표시되므로 중요한 정보를 그 안에 담습니다. 카드마다 Markdown 출처 링크와 `신뢰도: 공식`, `보도`, `커뮤니티`, `루머` 중 대표 값 하나를 적고, 출처별 차이는 본문에서 설명합니다.
- 템플릿의 5개 본문 카테고리를 사용합니다. 소식이 없는 카테고리에는 가짜 카드나 `신규 없음` 카드를 넣지 않습니다. `## 한계`, `## 짧게 남긴 시그널`, `## 실무 액션 아이디어`를 추가하지 않습니다. 실무 액션은 헤더 한 줄입니다.
- Top 카테고리 라벨은 `모델 · 플랫폼`, `콘텐츠 · 크리에이티브`, `마케팅 · 비즈니스`, `테크 · 인프라`, `규제 · 리스크`, `SNS · 트렌드` 중 하나를 씁니다. SNS 라벨은 현재 빌더 내부에서 에이전트 분류로 취급되는 한계가 있으므로 SNS를 Top에 넣으면 실제 이동 대상과 표시를 확인합니다.
- 기존 CSS·화면 JS·달력 생성 코드를 매일 수정하지 않습니다. 새 날짜 파일을 빌드하면 하단 월별 달력과 아카이브에 반영됩니다.
- 비스킷은 `site/biscuits_lib.py`와 `site/assets/biscuits.js`를 기준으로 확인합니다. 새로운 일반 개념이 꼭 필요하면 양쪽의 동일 ID·표제어·매칭 패턴과 JS의 카드·삽화를 함께 추가하고 `firstSeen`은 최초 해당 브리프 날짜로 둡니다. 벤더·제품 브랜드명은 용어사전에 넣지 않습니다. 기존 항목을 유지하고, 새 개념이 없으면 변경하지 않습니다.
- 비스킷 수정 시 `node --check site/assets/biscuits.js`와 전체 빌드를 수행합니다. 코드 편집·검증이 불가능한 환경에서는 용어 추가를 별도 미완료 항목으로 보고하고 사전 변경 없이 브리프를 검사합니다.

브리프 파일 전체는 공개 자료입니다. `내부 참고`라는 제목을 붙여도 비공개가 되지 않습니다. 개인 정보·인증값·공개하지 않을 작업 메모를 원문에 넣지 않습니다.

## 8. 저장과 검사: 환경에 맞는 한 가지 경로

### A. GitHub 파일을 직접 읽고 쓰는 AI 도구

1. `source`의 최신 SHA와 대상 날짜 파일 유무를 다시 확인합니다. 다른 작업자의 변경이 생겼다면 새 상태에 맞춰 통합합니다.
2. 사실·날짜·중복·Top 연결·미완성 자리표시자를 수동 검수합니다. 완성된 날짜 파일과 필요한 용어 수정만 포함해 `source`에 커밋합니다. 여러 파일 수정은 가능하면 한 커밋으로 저장합니다. GitHub 커넥터가 읽기만 가능하면 쓰기 성공을 가정하지 않습니다.
3. 푸시로 시작된 **`Validate source build`**에서 방금 저장한 **커밋 SHA**의 결과를 확인합니다. 다른 브랜치나 이전 커밋의 성공을 대신 사용하지 않습니다.
4. 실패하면 해당 실행의 로그를 읽고 필요한 부분을 수정한 뒤 새 커밋의 결과를 다시 확인합니다. 결과 조회가 불가능하면 `저장 완료·빌드 확인 대기`로 보고합니다.

개인 토큰이나 사용자 인증으로 한 커밋은 현재 push 검사 경로를 사용할 수 있습니다. GitHub Actions 안에서 기본 `GITHUB_TOKEN`으로 다시 커밋하는 완전 자동화는 별도 설계가 필요합니다. 후속 push 워크플로가 자동 시작된다고 가정하지 않습니다.

### B. 터미널이 있는 컴퓨터 또는 클라우드 작업 환경

새 작업 폴더가 필요하면 저장소 자체를 복제합니다. 예전 컴퓨터에서 파일을 전달받는 단계는 없습니다.

```bash
git clone --branch source --single-branch https://github.com/shinnarag/ai-brief.git
cd ai-brief
git status --short --branch
```

이미 복제되어 있다면 원격 저장소·현재 브랜치·미커밋 변경을 확인하고, 깨끗한 `source`에서 `git pull --ff-only origin source`로 갱신합니다. 다른 작업자의 파일을 초기화하거나 강제로 덮어쓰지 않습니다.

Python과 Node.js 버전은 `.python-version`, `.node-version`을 따릅니다. 아래는 macOS/Linux 예시이며 Windows에서는 생성한 가상환경의 Python 실행 경로로 바꿉니다.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/local.py build
```

완성된 브리프를 추가한 뒤 같은 빌드 명령을 다시 실행합니다. 화면 확인이 가능하면 다음 명령으로 당일 페이지의 Top 연결, 기존 비스킷, 월별 달력을 확인합니다.

```bash
.venv/bin/python scripts/local.py serve
```

미리보기는 `http://127.0.0.1:8765/`이며 종료는 `Ctrl+C`입니다. 빌드는 `site/public/`을 다시 생성하지만 이 출력은 커밋하지 않습니다.

다음 명령의 날짜를 실제 대상일로 바꿉니다. 필요한 다른 수정이 있으면 그 파일만 명시적으로 추가합니다.

```bash
git diff --check
git status --short
git add briefs/AI-Daily-YYYY-MM-DD.md
git diff --cached
git commit -m "Add AI Pulse brief for YYYY-MM-DD"
git push origin source
git rev-parse HEAD
```

푸시가 거절되면 원격 변경을 확인하고 통합합니다. 강제 푸시는 하지 않습니다. 그다음 A 경로와 같이 해당 SHA의 Actions 결과를 확인합니다. 웹 화면 또는 사용 가능한 GitHub 도구로 조회할 수 있으며 `gh` 설치 자체는 필수가 아닙니다.

### 검사의 의미

현재 빌드 검사는 주요 HTML·모든 브리프 페이지, JSON, 최신 페이지 연결, JavaScript 문법, 컴퓨터 고유 링크, 빌드 중 원본 변경 여부를 확인합니다. **사실성·기사 날짜·외부 링크 내용·의미 중복·전체 시각 품질은 자동 검사 범위가 아닙니다.** 따라서 위의 편집 검수를 따로 수행합니다. 원격 검사만 가능한 경우 로컬 화면을 확인했다고 보고하지 않습니다.

`workflow_dispatch`는 정의되어 있지만 기본 브랜치에 워크플로가 있어야 수동 실행을 사용할 수 있습니다. 현재 운영에서는 `source`에 저장할 때 실행되는 push 검사를 사용합니다. 이 문서를 이유로 기본 브랜치나 배포 설정을 변경하지 않습니다.

## 9. 완료 보고와 다음 단계

아래 네 상태를 구분해 짧게 보고합니다.

```text
작성: YYYY-MM-DD · 주제 · 본문 N개 / Top N개
저장: source의 원문 GitHub 링크 · 커밋 SHA
검증: 해당 커밋의 Actions 링크와 성공/실패/대기 · 수동 검수 범위
사이트 게시: 이번 작업에서는 미배포 (현재 source 빌드는 검사만 수행)
추가 사항: 신규 비스킷, 확인하지 못한 출처 등 있을 때만
```

공개 URL이 이미 존재하더라도 이번 원문이 배포되었다는 증거로 쓰지 않습니다. 게시를 별도 수행한 경우에만 배포 결과와 실제 당일 페이지 내용을 확인해 상태를 변경합니다. 저장 실패·빌드 실패·출처 확인 부족은 각각 어느 단계가 남았는지 명확히 표시합니다. 외부 메시지 전송은 기본 작업에 포함하지 않습니다.

향후 자동 배포는 `site/public/`만 Pages에 전달하는 흐름으로 연결합니다. 기존 배포 작업이 저장소 내용을 교체할 수 있으므로 먼저 운영 주체를 하나로 정리해야 합니다. 무인 작성은 이 편집 지침을 읽는 AI 실행기와 웹 조사·인증·예약·재시도 처리를 연결하면 됩니다. 둘 다 이 지침 파일을 추가한 것만으로 활성화되지는 않습니다.
